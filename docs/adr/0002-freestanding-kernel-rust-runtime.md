# ADR 0002: Freestanding kernel image hosted by a Rust runtime

## Status

Accepted

## Context

Upstream UML is an executable linked against the host C library, with host-side
code (`arch/um/os-Linux`) written against Linux libc headers. The Phase 0
prototype ported that layer to Renux (`os-Renux`) and hit two blockers:

1. Host libc headers collide with the kernel's freestanding include environment
   (`arch/x86/um/user-offsets.c`), requiring many compatibility shims.
2. The binary produced with the UML linker script aborts in the FreeBSD C runtime
   before `main`.

The host layer also grew into a large body of C emulating Linux libc behavior.

## Decision

Build the Linux kernel as a **freestanding** static ELF image (`-ffreestanding
-nostdlib`, LIU linker script, single exported entry `liu_kernel_entry`). A Rust
runtime (`liu-runtime`) loads the image, maps guest physical memory, and passes
two `#[repr(C)]` function tables:

- `liu_host_ops`: services the kernel calls (memory, address spaces, traps,
  time, interrupts, logging, device connections);
- `liu_kernel_ops`: entry points the runtime calls (interrupts, timer, faults).

The C side (`os-liu`) only forwards `arch/um`'s `os_*` contract to these tables.
The tables are defined in `liu-abi` and the C header is generated by `cbindgen`.

## Consequences

- Host libc and the host C runtime are no longer involved in the kernel build.
- All host logic is Rust: memory safety, testability, one source of truth for the ABI.
- The ABI can be exercised by a `no_std` test kernel without building Linux.
- The kernel and runtime share one address space; the runtime must be careful
  with signals and must not allocate inside handlers.
- Requires a patch to the `arch/um` build to support freestanding linking.

## Alternatives considered

- **Continue `os-Renux` in C, fix the linker script.** Rejected: keeps a large C
  libc-emulation layer and the header collisions.
- **Link a Rust staticlib into the UML executable.** Fallback if the
  freestanding build proves too invasive; still inherits the C runtime problem.
